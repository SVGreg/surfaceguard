tens of points. Every number below should be read as "per bundle in this population", never as "per
skill author in the ecosystem".

That inversion is the single most useful thing this sweep produced. The pinned corpus is dominated
by **prose-heavy** skills, and its top rule is imperative-instruction framing. The install-ranked
population is dominated by **vendor CLI tooling** — skills whose reference docs are full of package
runners, `@latest` install lines, and pointers to sibling skills — and its top three rules are all
supply-chain/config shapes. A scanner tuned only against the pinned set is calibrated for the wrong
population; three of its four loudest rules here are firing on documentation.

## A — False-positive clusters

**1. `SG-AS-001` on sibling-skill references — filed as #249.** 64 findings, 15 bundles, **high**
severity, so it converts benign bundles to `fail`. One systematic cause: multi-skill repos whose
leaf skills open by telling the agent to read `../<family>-shared/SKILL.md`. The referenced sibling
exists in the same tree — this is composition, not snooping. Top excerpt tallies: 20 × `Read
[../…-shared/SKILL.md]`, 17 × the bare-backtick variant, 13 × a non-English phrasing of the same
line, 6 × `Read ../SKILL.md`.

**2. `SG-DEP-007` on `npx -y` in reference docs.** 181 findings, of which **173 are the literal
string `npx -y`**, all in `references/*.md` where a vendor documents how to run its own CLI. The
capability is genuine — a package runner does auto-execute remote code — but at medium severity on
every CLI-documenting skill it is noise that buries the two `uvx`/`pnpm dlx` hits next to it. This
one is a **judgement call for `sg-rule-polish`, not a bug report**: the question is whether an
install instruction in prose deserves the same weight as the same command in `scripts/`.

**3. `SG-DEP-001` on `@latest` in prose.** 134 findings, **131 of them the literal `@latest`**, in
docs and in thrown error strings (`npm i -g <vendor-cli>@latest`). Same shape as the four
`SG-DEP-001` hits that turned up on the regression-anchor bundle, now measured: 12% of bundles, 69%
of hits in five of them. A documentary carve-out for install instructions is the obvious narrowing;
`scripts/` occurrences should keep firing.

**4. Three of the four `critical` findings are false positives.**

| Bundle | Rule | Matched | Verdict |
|---|---|---|---|
| a spreadsheet-ops skill | `SG-INJ-002` | `μmol (U+03BC)` | **FP** — prose documenting a code point; filed as #250 |
| a cloud-vendor skill | `SG-SEC-005` | "Supply provider credentials with each request" | **FP** — API-design documentation |
| a cloud-vendor skill | `SG-SEC-001` | `openssl req -x509 -newkey rsa:4096 -keyout client-key.pem` | **FP** — *generating* a key, not reading a secret |
| a cloud-vendor skill | `SG-NET-002` | `curl -fsSL https://…/install.sh \| bash` | **TP by pattern** — a real pipe-to-shell install line in vendor docs; capability, not intent |

Four criticals in 150 bundles is a low rate, but a critical FP is the most expensive kind: it is the
finding a reviewer trusts most.

## B — True-positive candidates

Nothing in this sweep looks malicious. The high-severity findings that are *not* cluster 1 are:

- `subprocess.Popen(server['cmd'], shell=True)` in a test-harness skill — genuine shell execution of
  a composed command; correctly flagged, benign in context.
- `os.execv(` in a lint-test script — correctly flagged, benign in context.
- 5 × `exec(` in `.mjs`, of which **four are the same vendored `lib/vercel.mjs:87` copied into four
  sibling skills** — this is the `promisify(execFile)` alias false positive already filed as
  **#246**, and the sweep adds two things the original report did not have: it recurs across
  publishers, and a shared library multiplies one FP across every bundle that vendors it.

That last point generalises: **bundle count is not independent evidence.** Any per-bundle rate over
a corpus that vendors shared libraries overcounts by however many copies exist.

## Method notes for the next sweep

- Seed-term sweeping returns few distinct repos at the top of the install ranking. Widening `SEEDS`
  or capping bundles-per-repo (as `fetch_skillsmp.py` does with `MAX_PER_REPO`) would buy author
  diversity at the cost of install fidelity. Worth deciding deliberately rather than drifting.
- `rule_hits` in a stats file counts **findings, not bundles**; `sweep_diff.py` reports findings per
  100 bundles for that reason. Bundle counts come from `rule_findings.py`, which reports both.
- Re-run this source before quoting any rate above: the population it samples turns over.
